## 未リリース

### FastAPI への書き直し

6,371 行の Django 実装が、FastAPI + SQLAlchemy 2.0 の 4,106 行になった。209 テスト通過。

**仕様に関わる部分は無改造で運べた。** `arkspec/` と `domain/resolution.py` の 680 行は
stdlib しか使わず、DB にはリポジトリ越しに触る作りだったので、import 元を変えただけで
済んだ。**97 本のテストがそのまま通った**ことが、この層を切り離しておいた価値を
いちばん明確に示している。

Django が構造で守っていた不変条件は、こちらでも構造で守っている——採番を単一の
INSERT 経路に閉じ、ローテーションを部分インデックスで表現し、ARK と shoulder の削除を
ORM の層で拒む。

### 認証

API に 3 機構。排他の選択ではなく**個別に有効化**する——移行期に「API キーと OIDC の
両方を受ける」が普通に要るため。どれで認証しても `Principal` 1 つに集約され、認可の
判断は 1 か所に留まる。

到達範囲を 3 段（`system` / `naan` / `manager`）にした。ARK の委譲の写しであり、
**配られた側が配った側より広く届くことはない。**

### 管理画面

テーブルではなく**操作**の形。日英対応。入口は 4 種類（`bearer` / `password` /
`oidc` / `proxy`）。

### 記録しておくべき修正

- **ビューで ORM のリレーションに代入していた**ため、表示から外した機関の `naan` が
  NULL になっていた。**読み取りの経路がデータを壊していた。**
- **機械の主体を前段のヘッダで名乗れた**。前段の設定を誤ると、誰でも一括投入バッチ
  として振る舞えた。人と機械を型で分けた。
- **PostgreSQL でしか出ないマイグレーションのバグが 2 つ**——`manager` と `shoulder` の
  循環参照、表の作成順。SQLite は両方通してしまう。
- **`oauth2` モードにトークン発行の口が無かった**。検証だけあって発行が無く、単体構成が
  実際には使えなかった。
