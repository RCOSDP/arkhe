    変更履歴¶

    書式は Keep a Changelog、版は SemVer。識別子を振り直せない体系で何を破壊的変更と みなすかは方針にある。

    未リリース¶

    0.1.0 — 2026-09-07¶

    仕様との差を埋め、外に向かって日本語で話すのをやめた版。 draft-kunze-ark-42 に 対する既知の不適合——MUST 4 件と SHOULD 3 件——がすべて無くなり、arkhe が自分の台帳の 外に出すものは英語になった。OpenAPI と、符号を持つ誤りの本文（文面ではなく符号で 判定できる）である。管理画面と ?info のページは、代わりに画面の言語で答える。

    公開している出力の形が変わる、最初の版でもある。 変わった形は下の「変更」と 「修正」に挙げてある。台帳そのものは触っておらず、マイグレーションは列幅の拡大だけ。

    追加¶

    • POST /api/import と /api/import/bulk で、外で採番された ARK を取り込める ようになった（1 本ずつでも、委譲した shoulder ごとまとめてでも）。公開側の下に閉じた arkhe を置く構成で、これが最大の穴だった——閉域で採った名前は公開台帳に載せられず、 禁輸が明けたときに別の ARK を採り直すしかなかった。閉じている間に配った参照が そこで全部死ぬ。これからは 行き先を 1 回書き換えるだけ で、同じ識別子のまま公開できる。

    取り込みは採番ではないので scope も別（ark:import）。採番は「番号をもらう」 操作、取り込みは「この番号だと言い張る」操作である。検査は 3 つでどれも緩めない ——shoulder が委譲されていること、名前がその内側にあること、検査桁が合うこと （外から来た名前を信じる手立てはこれしかない）。さらにその NAAN の権威をこの台帳が 持っていることも要る。到達範囲はほかと同じ規則で上位が下位を覆い、一括は 1 件でも 落ちれば 1 件も作らない——入ってしまった名前は引っ込められないからである。

    • PATCH /api/update は送った項目だけを書く。 同じパスの PUT は置き換えで、 title を省けば空になる——置き換えとしては正しいが、実際にいちばん多い「対象が 移った」には合わない。行き先を付け替えるのに記述を失わなくなった。空文字を送れば 今までどおり消えるので、値を消す手段も残っている（この 2 つは区別できなければ ならない）。

    • ?info は求められた媒体で答える。 §5.2 は「THUMP の応答の形は返す content type が示す」と書いている。既定は人が読むページ、Accept: application/json なら JSON、 Accept: text/plain なら ?? と同じ ANVL。中身はどれも同じ「記述＋永続性宣言」 である（§5）。?json は残す——その JSON を名指しする別名で、?info に同じ Accept を送ったときと同じものを返す。

    • ?info のページを翻訳するようにした。 ここは公開の口で、ARK は世界中から 引かれるのに日本語しか話しておらず、識別子は届いたのに説明が読めない状態 だった。管理画面と同じ catalogue から語を採る。永続性の水準の表示名も同じで、 それは ?json の commitment_label にも出る。この口で ?lang= は使えない ——クエリ文字列そのものが inflection なので、言語は & の後ろ（?info&lang=en）か Accept-Language で渡す。

    • 識別子 1 本を端から端まで追う手引きを足した （curl で採番から解決まで）。 採番、解決、suffix passthrough、修飾子 1 点の登録、対象の移動、保留、墓碑、 誤りの符号、リゾルバが自分について答えること。載っている応答はすべて、 動いているインスタンスから写したもので、手で書いたものではない。

    • 口ごとに、要求する scope が仕様書に出るようになった。 これまでは {"oauth2": []}——「トークンで入れる」とは書いてあるが、何が要るかは書いていない ので、仕様書から起こしたクライアントは全部入りの scope を要求するしかなかった。

      POST /api/mint {"oauth2": ["ark:mint"]} PUT /api/tombstone {"oauth2": ["ark:tombstone"]} POST /api/query {"oauth2": ["ark:read"]}

    scope を載せるのは oauth2 の要求だけ。bearer は type: http で、OpenAPI は oauth2 以外のスキームに scope を書くことを許さない（空配列でなければならない）。 宣言と本体の検査が一致することは、検査で固定してある。

    • トークンの取り方が OpenAPI に載るようになった。 securitySchemes に clientCredentials フロー（tokenUrl と scope の一覧）が無く、「これは OAuth 2.0 である」と機械可読な形では言っていなかった——エンドポイントの URL は README と 手引きにしか無く、仕様書からクライアントを起こすと認証の取得手順が落ちた。 Swagger UI の Authorize からもトークンを取れる。

    ARKHE_AUTH に oauth2 を含む構成でだけ載せる。 口の無い構成で広告すると、 生成したクライアントが取りに行って 404 を踏む。scope の語彙は authz.SCOPES から、 その説明は管理画面と同じ語から起こしている。

    • トークンを保ち回して使う作法を認証の手引きに書いた。 expires_in が尽きる手前で取り直すもので、API 1 回ごとに取り直すものではない ——発行のたびに client_secret を Argon2 で照合するので、そうすると apikey と 同じ重さを払ったうえに往復が 1 回増える。

    変更¶

    • /.well-known/ark は既定で text/plain を返すようになった（仕様どおり）。 draft-kunze-ark-42 §5.6 は ark を Well-Known URIs レジストリ（RFC 8615）に 登録し、応答を「リゾルバのルートパスを含む plain text、末尾は /」と定めている ——そこに compact ARK を継ぎ足すと解決の要求になる。arkhe は同じパスを先に独自の JSON 在庫に使っていたので、仕様どおりに読むクライアントからは「このホストに ARK リゾルバは無い」に見えていた。

      $ curl https://ark.example.ac.jp/.well-known/ark /

    在庫——預かっている名前空間、委譲した shoulder とその minter、止めている名前空間 ——は同じ URL の JSON 表現になった。Accept: application/json を付けて求める。 Accept を付けずにその JSON を読んでいたものには影響がある（中身は resolver_path が増えただけで変わらない）。どちらの表現にも Vary: Accept が付く。

    パスは ASGI の root_path から採るので、プレフィクス付きでマウントする構成は 設定すること（uvicorn --root-path /pid）——さもないと無い口を案内する。

    修正¶

    • 尾が行き先にそのまま連結されることを、手引きに書いた。 suffix passthrough は 名前より後ろを行き先に足すので、クエリを持つ行き先では尾がその中に潜り込む （…/view?id=1 ＋ /page/3 → …/view?id=1/page/3）。挙動は変えていない ——書かれていなかっただけである。

    • 分散の手引きが、保留をまだ「無い」と書いていた。 「転送を一時的に止める手段」が 無いものの節に残っていた——0.0.9 で入っている（ARK / shoulder / NAAN 単位、 理由と期限は公開され、時計で戻る）。そのとき消し忘れただけの項目である。

    • ARK の説明ページが短すぎ、行き先も示していなかった。 図が NAAN と name しか示しておらず、label・shoulder・blade・修飾子——何も引かずに文字列だけから 構造を読めるという要点を担う部分——が落ちていた。arks.org の定義に合わせて構成を書き直し（錠前の比喩も含めて）、このページは入口であって 体系そのものは arks.org にあると明記した。

    • クイックスタートの「手元で動かす」例では解決できなかった。 1 プロセスを起動して /ark:99999/… を叩いていたが、解決の口は ARKHE_RESOLVER=1 のときだけ生える ——1 プロセスでは 404 になる。分けてあること自体が設計なので、例も 2 つ起動する 形に直した。あわせて解析の誤りが二重に名乗るのをやめ （Not readable as an ARK: Not a valid ARK: missing name part）、 空の NAAN が「長すぎる」と言わないようにした。

    • 日本語版「壊さないもの」のページ内リンクが切れていた。 #ark が何も指して おらず、意図していた見出しは #ark-は削除しない。mkdocs はページ内アンカーの 切れを INFO で流すので --strict でも止まらず、見出しを書いた時点から静かに 死んでいた。check.sh と deploy-docs.sh で落とすようにした——読む側から見れば、 ほかのリンク切れと同じものだから。

    • 管理画面は言語を切り替えられるのに、断りだけ切り替わらなかった。 画面は ?lang= → cookie → Accept-Language で切り替わるが、断りの文面 15 か所—— 「この主体の範囲外」「NAAN 単位以上の権限が要る」、ログイン画面の「ID か パスワードが違います」——が直書きの日本語で、英語で使っていても いちばん困っているところで母語から落ちていた。画面と同じ catalogue から 採るようにしたので、片方の言語しか無ければ起動時に落ちる。

    • 起動時の設定エラーを英語にした。 Settings.check() は設定の欠けを配る前に 止めるもので、その文面は運用者の端末（コンテナのログ）に出る。arkhe がそこに 出す他の記録と言語を揃えた。

    • 誤りに符号が付き、本文が英語になった。 文面は変わる（分かりやすく直る、訳が 変わる）ので、文面で判定するクライアントは砂の上に立っていた。API と解決の口が 返す誤りは、すべてこの形になる。

      {"code": "ARKHE-1011", "message": "A request holds at most 1000 rows.", "detail": {"limit": 1000}}

    detail には文面を埋めた値が構造化されたまま入る。数字を文から切り出させない ため。解決の口は text/plain なので符号を行頭に置く （ARKHE-1403 ark:99999/x9abcd — Check digit mismatch: …）。

    一覧はエラーの参照ページ。 符号・状態符号・英語の文面・日本語の説明を 1 つの表（arkhe.errors）に持ち、 そこから起こしている——符号を足して書き忘れる、番号を再利用する、片方の言語 しか無い、のいずれも検査で落ちる。

    /oauth/token だけ意図して形が違う。 RFC 6749 §5.2 に従い （error / error_description。OAuth のライブラリがそう読む）、符号は併記する。 管理画面は自前の catalogue のまま——あちらは画面の言語で答えるもので、 この API の言語とは別だから。

    • 公開している OpenAPI が日本語だった。 FastAPI と Pydantic は docstring を description にするので、日本語でコメントしているこのコードでは仕様書も日本語に なる——読者はこの台帳の外にいて、日本語が読めるとは限らないのに。

    仕様書に出る文字列をすべて英語にした。概要、タグ、各エンドポイント、各応答符号、 リクエストのスキーマとその項目、2 つの認証スキーム。docstring は日本語のまま 残す——あれは実装を読む人のためのもので、読者が違う——ので、英語は description=（ルート）と model_config（モデル）で明示的に渡している。 FastAPI も Pydantic も、渡された側を docstring より優先する。

    生成した仕様書を両方の役割で走査して CJK があれば落ちる検査を置いた。口を 足すたびに人が思い出す前提にしない——渡し忘れると docstring がそのまま 仕様書に漏れるので、漏れたことに気づく手立てをコードに持たせる。

    • 経路照合がラベルの大小を見ていた。 parse_ark は §3.2 手順3 のとおり最初から 大小非依存だったが、HTTP のルートは字面どおりだったので /ARK:/99999/x9abc は リゾルバに届かず 404 になっていた。経路照合の前にラベルの 5 文字だけを 小文字に直すようにした。名前の大小には触らない——そちらは識別子の一部である （手順5）。

    • THUMP の応答ヘッダが無かった。 §5.2 は inflection の応答に THUMP-Status と Link を示し、後者の役目まで書いている——inflection を知らない受信者に、この 応答が「修飾の付いていない ARK」を記述したものだと示すためのもの。識別子に ついてリゾルバ自身が答える応答（? ?? ?info ?json、記述、保留、404） すべてに付け、転送には付けない。

    rel の綴りは仕様の応答例（<…> rel="describes";）ではなく <…>; rel="describes" にした。例のほうが RFC 8288 のリンク値として不正で、 そのままでは標準のパーサが読めない——同じことを、通じる形で言う。

    • ERC の where に転送先を入れていた。 §5.1.2 は where を「一時的な転送先では なく長期的な識別子」と定めているのに、arkhe は逆で、ARK は行き先が空のときの代替に していた。記述は「この識別子が何を指すか」を答えるものなので、行き先と一緒に動く 値では引用できない。where を compact ARK にし（付け替えても動かない）、今の 行き先は kernel の外の redirect として、あるときだけ出す。? ?? ?json と ?info の画面が変わる——where から行き先を読んでいたものは redirect を見ること。

    • 新しい ARK を旧形式の ark:/ で生成していた。 §2.2 は「新旧どちらのラベルも 永久に認識しなければならない。ただし新しい ARK は新形式で生成すべき」と 定めている。arkhe は受理は両方できていたが、出すものはすべて旧形式だった ——配った文字列がそのまま次の実装の入力になるので、これでは旧形式が減らない。

    生成をすべて新形式（ark:99999/x9abc）にした。API 応答の ark、ERC の where と about、?json、404 の本文、他のリゾルバや N2T へ取り次ぐときの Location、 CLI の ark list、管理画面。表記を決める場所は 1 つにしてある （arkspec.naming.compact_ark）ので、また片方だけ残ることはない。

    受理は変えていないし、狭めない。 ark: も ark:/ も裸の 99999/x9abc も 同じ識別子に当たる。これは検査で固定してある。

    公開している出力の形が変わる——API 応答や CLI の行から ark:/… を切り出している ものは ark:… を受けられるようにすること。台帳は触らない（保存している鍵に ラベルは最初から入っていない）。

    • 列の幅が 2 つ、仕様が受け取る側に義務づける下限を割っていた。 NAAN は 10 オクテットを超えると拒否し、名前は varchar(100) に入れていたが、 draft-kunze-ark-42 は NAAN 16 オクテット（§2.3）と Base Name ＋ Qualifier 255 オクテット（§3.1）への対応を要求している。

    NAAN の 10 には理由があったが、ここには当てはまらない理由だった。arklet は NAAN を int() に通すので len(naan) > 10 で変換を守る必要があり、その定数が解析処理ごと 移ってきていた。arkhe は N2 で逆を決めている——NAAN は文字列として保持・比較し、 整数化しない（ark:/099999/… と ark:/99999/… を別物とするため）——ので、 守るべき変換がそもそも無かった。

    naan.naan を varchar(16)、ark.assigned_name を varchar(255)、台帳の鍵 ark.ark を varchar(272)（16 ＋ / ＋ 255）にし、NAAN と ARK を入れる列を すべて揃えた。PostgreSQL ではメタデータだけの変更で、テーブルの書き換えも索引の 作り直しも起きない。255 を超える名前は DB のエラーではなく、上限を示した 400 で断る。

    • 名前のなかの %2F が、黙って成分の区切りにされていた。 ASGI はアプリに渡す前に 経路を復号するので、ark:/99999/x54%2Fc2 は x54/c2 として届いていた—— 別の識別子である。予約文字を %-エンコードしてよいのは、まさにその予約された 意味を隠すため（draft-kunze-ark-42 §3.2）で、%2F は「成分を区切らない /」を 意味する。復号すると、suffix passthrough が無関係なレコードの行き先を継ぎ、 グローバルリゾルバへは書き換わった ARKを渡していた。%7D も同じで、復号形の } は §3.1 の文字集合にそもそも入っていない——エンコードが唯一の合法な運び方で ある。仕様は名指しで禁じている: no %-encoded character should ever appear in an ARK in its decoded form.

    解決は ASGI の raw_path からエンコードを保ったまま経路を読むようにし、16 進の 大小を揃える正規化（%2f → %2F。手順5）を解決側と登録側の両方に通した。 /a%2fb で登録した修飾子が /a%2Fb の要求で当たる。前段のプロキシもエンコードを 素通しにすること——nginx と Apache の設定は API リファレンスにある。

    • 一括採番で、同じ request_id が 1 回の要求に 2 行あると 500 で落ちていた。 控えは (client, request_id) で一意なので、控えを 2 度書こうとして IntegrityError に なり、1 件も採番されずに終わっていた。同じ request_id は「同じ 1 つの依頼」の 意味なので、1 件だけ採番して両方の行に同じ ARK を返すようにした——再送の扱いと 同じ約束を、塊の内側にも通す。

    • 応答の符号と媒体が仕様書で不足していた。 再送のときの 200（POST /api/mint と /api/mint/bulk）と、解決の 3xx / 400 / 404 が宣言されておらず、生成した クライアントがそれらを「知らない応答」として扱う形になっていた。解決の 200 も application/json しか宣言しておらず、ANVL（text/plain）と ?info の HTML が 漏れていた。転送は 301 / 302 / 303 / 307 の 4 通り（shoulder の委譲テンプレートが 先頭に符号を書ける）。宣言と実装がずれないよう、検査で突き合わせている。

    • 公開している API 仕様で、採番と解決の口だけ説明が空だった。 FastAPI は docstring を OpenAPI の description にするので、POST /api/mint POST /api/mint/bulk GET /ark:… の 3 ハンドラ（4 オペレーション）に説明が載っていなかった——他の 9 口は 揃っていたので、いちばん使われる 2 本だけが空という形になっていた。 再送の扱い（201 と 200 の区別）、一括採番の全か無か、解決が 302 以外を返す条件を書いた。

    • 手のひらの幅で表がはみ出し、右側の列が読めなかった。カードに overflow: hidden があるためページは伸びず、代わりに切り取られていた。 640px 以下では 1 行を 1 枚に畳み、各値の前に見出しを出す。
    • 狭い画面ではログアウトが押せなかった。 サイドバーの底に名前の無いアイコンと して置いてあり、860px 以下ではそのサイドバーごと畳まれていた。ヘッダーに移した。
    • 日本語の見出しのアンカーが _1 _2 … になっていた。既定の slugify が非 ASCII を 落とすためで、日本語ページへの深いリンクが使えず、見出しを 1 つ足すと番号が ずれて既存のリンクが黙って別の場所を指していた。
    • 変更履歴を書いても公開が追随しなかった。docs ワークフローのパス条件に CHANGELOG*.md が入っていなかった（本文は --8<-- で取り込んでいる）。
    • バージョン方針のページに版番号を直書きしていて、0.0.1 のまま古くなっていた。 リリースのたびに古くなるものは文書に書かない。

    0.0.3 — 2026-08-29¶

    管理画面が、採番だけの画面から台帳を組める画面になった。0.0.2 と同じく、 出てきた欠陥はどれも実際に画面を触って見つけたもので、テストでは 1 つも 出ていない。

    追加¶

    • 管理画面から台帳を組めるようになった。 一覧にあった「NAAN を登録」 「組織をオンボード」「shoulder を切り出す」「操作」の 4 つのボタンは、 いずれも存在しないルートを指していて 404 だった。実装し、NAAN と組織と shoulder の設定画面も足した。
    • 約束の水準を設定できるようになった（arkhe manager commitment、 arkhe onboard --commitment、管理画面）。? と ?? で公開されるのに設定する 手段が無く、全組織が既定の permanent-dynamic を名乗ったままだった。組織が 述べていない約束を組織の名前で名乗ることになる——宣言していないものを宣言と して出すのは、何も出さないより悪い。 --commitment を付けずに迎えた場合は その旨を stderr に出す。未知の水準は拒む。 その組織の管理者自身も変えられる——約束は組織自身のもので、述べる主体が 述べられなければ意味がない。
    • arkhe manager list。組織の id は他のコマンドの入力になるが、一覧する手段が 無かった。
    • set_quota。採番上限をオンボード時にしか決められなかった。自組織では 変えられない——課された側が外せる上限は上限ではない。
    • コマンドが日本語と英語を話す。 言語は起動時に環境から決まる（ARKHE_LANG、 次に LC_ALL / LC_MESSAGES / LANG を POSIX の順で見て、既定は管理画面と 同じ ja）。Typer が help を組み立てるのは import の時点なので、実行時の --lang は作れない。
    • 一から立ち上げるときの手引き（日英）。arkhe の外で起きる手順——NAAN の 申請と、NAAN registry への解決先 URL の登録——も含めて並べた。後者が抜けると n2t.net/ark:/99999/… は自分のところに届かない。
    • compose/oidc/lan.yml。LAN の別の端末からデモを見るための上書き。公開先を 0.0.0.0 にするだけでは足りず、issuer と redirect_uri はブラウザが実際に打つ URL でなければならないので、ARKHE_DEMO_HOST で受け取り、redirect は realm JSON に焼き込まず起動時に登録する。既定の待ち受けは 127.0.0.1 のまま——この一式は 秘密値を平文で持っているため。

    変更¶

    • 画面の言葉を、台帳を初めて見る人に向けて書き直した。 一覧の名前は 「委譲の構造」から 組織管理 へ。ボタンは何が起きるかを述べる形にした （「組織をオンボード」→「組織を追加」、「shoulder を切り出す」→ 「名前空間を追加」）。組織を追加する画面には、同時に名前空間を渡すことを 最初に書いた。「主体と資格情報」は「利用者と鍵」に——ここに並ぶのは組織そのもの ではなく、組織のシステムと人だから。採番の欄は「shoulder」ではなく 「採番する名前空間」に（選ぶのは NAAN と shoulder の組であって shoulder だけ ではない）。約束の水準が生の値のまま出ることも無くなった。
    • 用語は捨てず、括弧で残す。「名前空間（shoulder）」「永続・内容は変わりうる （permanent-dynamic）」のように平易な言い方を先に置いて用語を添える。初めての 人はそのまま読め、用語を知っている人は仕様・CLI・API と対応が取れる。
    • 名前空間を渡す先を指す語を「機関」から 組織 に統一し、NAAN を 「組織番号（NAAN）」と呼ぶことにした（Name Assigning Authority Number で、 番号を持つのは組織のほう）。画面・コマンド・エラー文言・文書まで通して揃えた。
    • 画面の「利用者」と、API・CLI の「主体（principal）」が同じものであることを 文書に明記した。読み手が違うので呼び方は分けたままにしてある。対応表を 管理画面とコマンドの両方のページに置いた。

    修正¶

    • ログアウトできなかった。 こちらのセッション Cookie は消していたが、認可 サーバのセッションはそのままだったので、次に画面を開くと何も訊かれずに戻って きていた。OIDC の構成では認可サーバ側も終わらせる（RP-Initiated Logout）。 id_token_hint は渡さない——渡すには ID トークンを Cookie に抱えることになり、 claim の多い環境で 4 KB を超えてブラウザに黙って捨てられ、今度はログイン できなくなる。end_session_endpoint を持たない認可サーバではこちら側だけで 終える。
    • NAA ポリシーを組織管理者が書き換えられた。 これは名前空間を配る側の宣言で NAAN 配下の全組織にかかるので、1 組織が他組織の分まで言い直せてはならない。 NAAN 単位以上を要求するようにした。組織が自分について述べるのは約束の水準の ほうで、そちらは組織管理者が変えられる——この分かれ方は権限表ではなく、 ARK の委譲の構造がそのまま出たもの。
    • NAAN の設定画面を組織管理者が開けてしまい、保存で 403 になっていた。編集できる ように見えて保存できないフォームは、ボタンが出ないのに URL は通るのと同じ欠陥 なので、開ける条件を保存できる条件に揃えた。

    0.0.2 — 2026-08-28¶

    すべて、0.0.1 を Kubernetes と compose に実際に載せて出たもの。テストでは 1 つも 出ていない——4 件とも「コードが正しい」と「デプロイできる」の間に落ちていた。

    修正¶

    • /healthz をどのモードでも載せた。resolve ルータにしか無かったので、minter と admin は liveness probe に 404 を返し続け、繰り返し殺されていた。
    • resolver に認証設定を要求しないようにした。認証を通す口も管理画面も無いのに、 起動時に ARKHE_SESSION_SECRET と OIDC の設定を求めていた——使いもしない セッション署名鍵を、解決系の全ノードに配らせていたことになる。
    • shoulder を指定した主体が組織を継ぐようにした。--shoulder だけ渡すと manager が空のまま作られ、認可の入口で必ず弾かれていた。しかも「shoulder は 合っているのに通らない」という追いにくい形で。shoulder と食い違う manager を 明示した場合は、黙ってどちらかを優先せず拒む。
    • ラベルの一意性は、ラベルがあるときだけにした。(manager_id, label) の一意制約に 空文字が含まれていたため、1 組織にラベル無しの主体を 1 つしか置けなかった。 プロセスごとに鍵を分ける普通の構成（web-api / web-ui / worker）が通らず、 鍵を共有させる圧力になっていた。移行は 56e5e54db345。
    • compose のブラウザログインが invalid_scope: openid profile email で落ちていた。 realm の import で clientScopes を宣言すると Keycloak 組み込みの一式は追加では なく置き換えになるため、profile と email が realm に存在していなかった。

    変更¶

    • デモ realm の defaultDefaultClientScopes から arkhe-api を外した。realm の 既定に入れていたので、後から作ったどんなクライアントでも arkhe 宛だと名乗れる トークンを取れた。audience は「このトークンがどの API 向けか」の宣言であって、 既定で配るものではない。
    • compose の resolver を独立したサービス（:8058）にした。デプロイ時と同じ形に なるうえ、Keycloak を止めると採番が 401 になり解決は 302 のままであることが、 そのまま見える。

    0.0.1 — 2026-08-28¶
