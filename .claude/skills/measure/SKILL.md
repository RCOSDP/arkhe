# 測る

**測り方を間違えると、以降の判断が全部ずれる。** 実際、最初の掃引は
**クライアントの天井の上で測っていて、worker 数に対して単調ですらなかった**。

## ① クライアントが天井でないことを、先に確かめる

`scripts/bench.py` は **1 プロセス約 2,200 rps で頭打ち**になる（GIL）。
**同時数を上げても動かない。**

```bash
python scripts/bench.py http://HOST/healthz -n 6000 -c 8    # DB も認証も通らない口
```

**測りたい値がこれの 7 割を超えていたら、測っているのはサーバではない。**
プロセスを並べて合計する（4 つで約 9,000 rps まで上がる）:

```bash
for i in 1 2 3 4; do python scripts/bench.py "$URL" -n 3000 -c 8 & done; wait
```

## ② ばらつきを知ってから、差を語る

同じ条件の測り直しで **±20% 振れる**（同居した 1 台で測る限り）。
**この幅より小さい差は、意味のある差ではない。**

- 「1 → 2 → 4 worker の倍々」は幅の外——**差である**
- 「8 → 16 worker の 1.1 倍」は幅の内——**差ではない**

最低 2 回測り、良いほうではなく**両方**を見る。片方だけ載せない。

## ③ 時間で見えないものは、数えて見る

**rps は雑音に埋もれるが、回数は埋もれない。**

`pool_pre_ping` の効果は rps では見えなかった（1,182〜1,528 と振れる）。
**DB の往復を数えたら決定的だった**——1 件あたり 1.60 → 0.82。

```sql
-- 要求 N 件の前後で差を取る
SELECT xact_commit + xact_rollback FROM pg_stat_database WHERE datname='arkhe';
```

キャッシュの効きも同じ（`blks_hit` / `blks_read`）。**構造が変わる調整は、
時間ではなく回数で確かめる。**

## ④ 効かないと分かっていることを、先に知る

**測って効かなかったもの**（[デプロイ](../../../docs/guides/deployment.ja.md)に一覧）:

- `uvloop` / `httptools`
- `shared_buffers`（128MB でも命中率 99.95%）
- 接続プールを 30 倍
- `synchronous_commit=off`（採番の 60 ms のうち 53 ms は Argon2）

**効いたのは `pool_pre_ping` だけ。** 新しい調整を試す前に、ここを読む。
